Limen roles, the agent loop, and steering

Limen lets one person run many coding agents. This page shows who does what, how one job runs from start to land, and how messages reach an agent while it works.

Based on the Limen repository on 6 October 2026: docs/jobs.md, docs/groups.md, docs/finish-webhooks.md, templates/ and hook/. A uncertain label marks a point that the files do not settle.

1. The roles

Two roles are people or outside assistants. One role is an interactive chat session. The rest are Limen jobs: each job has its own Git worktree and its own branch.

Operator (Adam)

The one human. He owns the project.

May
Say the outcome he wants. Answer product questions. Own spec/vision.md. Review work before it lands (the board says Adam reviews; no extra reviewer unless he asks). Type directly into a hosted job's tab.
Usually not
Run the harness commands. The coordinator types them. The docs say: speak when something looks wrong, or when the coordinator asks.
Starts
Not started by Limen. He opens the coordinator tab in Herdr.

Shepherd agents

Johnny, Tony, Easy and others: outside chat assistants that start and watch work for a plant.

May
Receive the plant's webhook pings: job done, failed, timed out, stalled, stopped; coordinator idle, blocked, goal done, exited; lead step done. The tickets say a shepherd also reads panes and steers a lead by hand.
Must not
Treat a ping as ownership. The webhook doc says a wake reports the finish; it does not transfer ownership.
Starts
Outside Limen. Limen only sends HTTP pings to the targets in the plant's private .limen/finish-webhook.env. uncertain How each shepherd sends work into a plant is not described in this repository.

Plant coordinator

The interactive agent session for one project (a "plant"). Adam talks to it.

May
Write tickets and keep the board (spec/build.md). Decide spawn and merge. Run limen spawn, steer, stop, continue, land.
Must not
Rewrite the vision without asking. Spawn a "coordinator" or "lead" job: spawn --role coordinator and --role lead are refused.
Starts
A hosted tab in the plant's Herdr space, preferably OMP, with LIMEN_COORDINATOR=1 and the Limen hooks loaded. It is not a Limen job.

Group lead

The same plant coordinator tab, when it runs a team group on one feature.

May
Run limen group start, status, publish, stop, close. It is the only landing owner of the group. It writes group/findings/ and group/synthesis.md.
Must not
Be a spawned job. A job tab has LIMEN_JOB=1, and group start refuses it. No automatic merge, no restart of a team coordinator.
Starts
Not started. The coordinator tab becomes lead when its group-peer hook is live. The hook refreshes a file in .limen/group-leads/ about once a second; group start refuses a file older than 30 seconds.

Team coordinator

One per team in a group. It tries one approach to the feature.

May
Spawn its own team's workers with the recorded model settings, within a fixed launch allowance. Merge its own team's branches into its candidate. Publish findings with limen group publish. Wait with limen group wait (20 seconds at most per call).
Must not
Push, merge into main, edit the board, or run limen land. Touch another team's jobs. Start helper agents or another coordinator. It gets one launch only: no continuation.
Starts
Only through limen group start, as a Limen job. --detached runs it in the background; --tab runs it in a Herdr tab.

Worker

The default job. It does one task in one worktree.

May
Read, edit, run checks, and commit on its own branch limen/<job-id>. Write a notes file.
Must not
Edit the board, the ticket status, or outcome files. In a group, it cannot spawn jobs.
Starts
limen spawn. When Herdr runs, the default is hosted: the agent runs in its own Herdr tab and a person can type into it. --detached runs it in the background; its tab shows only a log.

Reviewer, and other job roles

Jobs with a different role file. --role <name> loads templates/<name>.md, or the project's own copy in .agents/limen/.

Reviewer
Started with limen spawn --review --detached --branch limen/<job-id>. It checks a candidate and answers PASS <sha> or FAIL <sha>. It must not rewrite the candidate. The coordinator files the answer as review-N.md. On this plant Adam reviews, so a reviewer runs only when he asks.
Others
research (answers one question from named sources), quality (writes spec/quality/YYYY-MM.md), picture (writes the local map), judge. None of them merges or edits the board.

2. The agent loop

Every job follows the same path. It starts from a task file, works in its own branch, and ends with a state file. Then the right people hear about it, and the coordinator decides whether to land it.

A done job is not approved. done means only that the run exited cleanly. limen land runs no tests and no review. It checks that the job is done, the target branch is checked out and clean, and the branch has commits. Then it runs git merge --no-edit. Checks and review happen before, by the coordinator and Adam.

3. Steering and injection

An agent sees text from four places: its start-up prompt, its task file, a hidden note on every turn, and short notes added after some tool results. People can also steer a running job.

Steer and continue

  • limen steer <id> "text" works only on a running job with a live process. It writes the text to the job's steer/inbox/ folder.
  • The steering hook inside the job picks it up and hands it to the agent as a steer message, between tool calls. It logs steered: ….
  • limen steer --running "text" sends to every running job that this coordinator watches.
  • limen continue <id> "text" needs a finished job. It makes a new, linked job that keeps the old conversation, worktree and branch. Only committed work is safe after a prune.
  • A steer that never arrived is listed in the finish wake.
  • Group members cannot steer, stop or continue another team's job.

Where context comes from

  • Task file .limen/jobs/<id>/task.md: the coordinator's instruction, with a Ticket: path.
  • Ticket: the agent reads it from the path. Limen does not paste it into the prompt.
  • Role file and speech register: templates/<role>.md and templates/communication.md, or the project's own copies in .agents/limen/.
  • Group packet: the participation rules plus paths to brief.md and the team note.
  • Peer findings: only through the group-peer hook.
  • AGENTS.md and README: Limen adds the shop manual to the coordinator only when the project has no AGENTS.md. uncertain Whether OMP or Pi itself loads AGENTS.md or the README for a job is engine behaviour, not Limen code.

How the finish signal travels back up

Workers inside a team never wake the lead directly. An HTTP accept from the webhook does not prove that the shepherd read it. The coordinator can always read .limen/jobs/<id>/state when a wake does not come: the job files stay the source of truth.

4. Worked example: a group run from start to land

Two teams try two approaches to one feature. The lead compares them, and Adam decides what lands.

  1. Adam asks for the feature.

    He tells the plant coordinator the outcome and asks for two teams with different approaches. Groups start only when the owner asks.

  2. The coordinator writes the packet.

    It writes ticket.md, group/brief.md, group/teams/team-1.md and team-2.md, updates the board, and commits them.

  3. The lead starts the group from its own tab.

    All limits are required and recorded. The last output line is the group id.

    limen group start spec/features/active/FNNN-name \
  --teams 2 --workers-per-team 2 --timeout 30m --worker-timeout 20m \
  --engine omp --provider P --model M --thinking xhigh --worker-thinking high --detached
  4. Each team coordinator states its idea first.

    Its first action is limen group publish "Initial hypothesis: …", before it reads any peer finding. Then it spawns its own workers with limen spawn.

  5. Workers build; teams share findings.

    Workers commit on their own branches. Teams publish findings and questions. Peer messages arrive after tool results. Idle coordinators call limen group wait again and again until their work is done or the deadline comes.

  6. Teams finish.

    Each team coordinator merges its own team's branches into its candidate, publishes a summary with commits and checks, and ends. The lead gets each finish as a group event.

  7. The lead compares and writes synthesis.

    It writes group/findings/ and group/synthesis.md and commits them. This turn sends lead.step-done to the shepherd, with the hand-off "owner decision on group/synthesis.md, or close the group".

  8. Adam decides; the lead lands.

    The lead runs limen land <team job id> on main, then git push origin main, then limen group close <group id>. Close refuses while a member is live or a worktree is dirty. The coordinator adds outcome.md, moves the folder to done/, and marks the board 🟢 PROVEN.

uncertain Step 8 joins the general rules: the lead is the only landing owner, land merges a done job, and the board records who pushes main. The docs do not give one fixed land recipe for a group.
