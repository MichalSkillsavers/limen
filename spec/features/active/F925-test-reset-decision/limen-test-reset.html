Limen's tests: rebuild them small

Limen has more test code than product code, and most of it guards nothing real. Three agent teams studied every test file on 6 October 2026. This page gives their verdict, what must never break, and the plan.

Decision only. No test was deleted in this run. Feature F925. Notes: spec/features/active/F925-test-reset-decision/group/ in the Limen repository.

Verdict

Rebuild the tests from scratch, one area at a time.

Each new test replaces old tests in the same step. The old tests stay only until their replacement works. Do not trim the old tests again: the last trim grew back in 11 hours.

The one decision for Adam

Approve the rebuild with a hard limit of 3,500 lines of test code, written as one line in the vision file that only you edit. The rule that stops the tests from growing back depends on that number living in your file.

1. Why now

The tests grow faster than the product. Half of the lines check something that is not the real product. And a full run takes so long that nobody runs it before a change goes in.

  • Slow: one full run took 1,502 seconds (25 minutes) for 532 tests. Most of that time goes into each test building its own practice project and fake agent.
  • Not run: because the run is slow, changes land without it. In the night of 5 to 6 October, the main branch had failing tests twice.
  • Fragile: tests that use a stopwatch fail at random when the Mac is busy, then pass on a second try.

2. Three ways to do it

Team 3 argued against a full rip-out. It found a real risk, and the plan keeps it covered.

The five known failures that must stay guarded during the rebuild: (1) two agents registering a project at once lost one of the records; (2) a finished job woke the coordinator twice; (3) a team member failed to start behind a slow teammate; (4) a background status check blocked a worker's save; (5) a live job was marked failed when its tab lost track of it. Each new test must fail on the old, broken code before the old test is deleted.

3. What must never break

Ten areas, one test story each. Each story runs Limen for real on a throwaway practice project, with a fake agent in place of a real model. No story waits on a stopwatch.

1 · Start a job

A task becomes a job with its own copy of the project and its own branch.

Catches: a job that writes into another job's copy; a task that arrives changed.

2 · Start a job in a visible tab

The same, when the agent runs in its own tab.

Catches: a job that never ends; a live job marked failed.

3 · Finish and wake

A job ends as done, failed, stopped or timed out, and the coordinator hears about it once.

Catches: a lost or double wake; an error recorded as done.

4 · Steering and context

A message sent to a running agent arrives once. Every agent gets the house rules, the vision and the board.

Catches: a lost steer; an agent that starts without the rules.

5 · Land

A finished job's work goes onto the main branch only when it is safe.

Catches: landing a running or empty job, or onto unsaved changes.

6 · Spec keeper

New tickets get the next free number and correct links; a bad ticket cannot land.

Catches: two features with one number; a ticket with broken links.

7 · Webhooks

Finish messages reach only the allowed outside assistants.

Catches: a message to the wrong place; a password in a log.

8 · Team groups

Several teams work on one feature with fixed limits.

Catches: two members in one slot; a lost team result.

9 · Clean-up

Finished and dead jobs are cleaned up; live work is never deleted.

Catches: deleted live work; leftover processes after a stop.

10 · GitHub doorbell

A mention on GitHub starts work only for allowed people.

Catches: a stranger starting work; a reply posted twice.

Nine small checks of tricky logic stay beside the stories, for example ticket rules, the webhook password checks and job numbering. The live map page is a view, not one of these areas: it keeps only the small checks that the ticket rules share.

5. The plan

Agents do the work. Adam answers one question at the start.

  1. Adam approves the 3,500-line limit.

    One line in the vision file. Only Adam edits it.

  2. Freeze the old tests.

    From now on, new work adds no lines to old test files. New checks go into the new tests only.

  3. Build the shared practice project.

    One helper creates a throwaway project, a fake agent and a fake webhook receiver for every story. The limit check goes in at the same time.

  4. Write the stories in two waves.

    First the five areas whose old tests take the most time: team groups, visible tabs, webhooks, starting a job, steering. Then the other five and the small checks. Each step deletes the old files its story replaces.

  5. Prove the five known failures are still caught.

    Run each new test against the old, broken code. It must fail there and pass on today's code. Only then delete the old test.

  6. Delete what is left of the old tests.

    Run four test files at once to save time.

  7. Measure and check by hand once.

    One full run on a quiet Mac, with the real time written down. One run with a real visible tab, because the fake tab can drift from the real one.

6. The rule that stops the tests from growing back

A limit that a feature can raise in its own change is not a limit. The old size limit on product code was raised 50 times in 37 days, each time inside the feature that needed more room, and then deleted.

  • The number lives in Adam's file. The vision says: test code stays at or under 3,500 lines. No agent edits the vision without asking.
  • The test run checks it. Over the limit, the run fails with a plain message: remove this many test lines, or ask Adam to raise the limit.
  • Each landing reports it. When a change lands, Limen prints the test line count, the limit and the change's own count. It informs; it does not block, as the vision asks.
  • It works because the run is fast. A 4-minute run gets run before a change lands. A 25-minute run does not.
  • If it is ever broken: the next step is a stricter rule — a change that adds test lines must remove as many.

7. What we knowingly stop testing

These checks go and get no replacement. Each one guards a warning light, a display, a Linux-only path or a speed fix, not a result a user depends on.

  • Early warning when an agent's tool stops doing work. The job's own time limit still ends it.
  • Warning lights on visible tabs.
  • A Linux-only tab feature that never runs on this Mac.
  • The layout, colours and wording of status screens and the live map page.
  • A speed fix for the clean-up sweep.
