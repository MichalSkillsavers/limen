# Challenger: replace the safety net before removing it

**Verdict: staged replace, not a wholesale rip-out or another trim.** Build a small scenario set and retain only regressions for incident-backed transitions until equivalent tests pass. Delete each legacy cluster when its replacement covers the same failure, not when the new suite merely exercises the same command. This respects the owner's request to remove unessential tests without opening a window in which a known race or trust boundary has no proof. Target about 3,000 test lines, six minutes serial and 3–4 minutes with independent scenario files run four at a time on a quiet Mac; these are design estimates from Team 2's measured 3.6-second init/spawn/wait round trip at load 108, not from a completed replacement suite.

## Three paths

| Path | Estimated route to ~3,000 lines and a six-minute serial run | Unprotected interval and unseen failures |
| --- | --- | --- |
| Rip out everything, then rebuild | One removal plus one ten-scenario build wave: about two focused working days if replacement really covers every seam. Fastest reduction in test runtime. | From deletion until scenario and edge checks pass, **all** known race/security cases above have no regression. A clean happy-path suite can still miss stale-lock reclamation, duplicate wake claims, hostile webhook destinations, or dirty-target refusal. |
| Stage replacements by seam, then remove old clusters | About three focused working days across scenario build and per-cluster cutovers; targeted files run during work, with the full 25-minute baseline run only at integration. End-state runtime improves as clusters leave. | No intentional gap: preserve each old incident guard until an equivalent new check passes. Overlap temporarily retains some slow tests and requires mapping each failing-state invariant. |
| Keep the suite and cut low-signal cases again | A day for another trim, but reaching ~3,000 lines needs many later cuts and an architectural change; F776 already shows 1,543 lines grew back after its merge on the same day. | No immediate regression gap if only duplicates go; the 25-minute feedback loop, flaky clock assertions and test churn persist while the cut is incomplete. |

Day counts and replacement run times are **planning estimates**, not measured agent throughput. A staged path is the fastest safe end state because the full restart's apparent two-day speed excludes its period without any regressions. The pre-fix replay set is closed: registry ordinary/stale lock (`4e84296^`, `8548de0^`, `996bba9^`), batched and two-listener wake (`7e43d23^`), group cabinet/launch lock (`b62b837^`), index observation (`43c01cf^`), and hosted missing-row recovery (`88fd5ac^`, already demonstrated red in `7cbce5c`). If a CLI change prevents an old-commit scenario, run its narrow invariant check against the old logic; if neither runs, retain the current guard or name the uncovered proof as an accepted owner-reviewed risk. No pre-fix replay for tests with no evidenced historical defect. Record each failure mode, old test, new scenario/edge check and replacement proof. At landing, the owner reviews added test lines and requires a replaced cluster or a newly demonstrated failure mode; a self-editable numeric budget alone will not stop regrowth.

## Points from other teams

- Team 2's checked draft `a5fda8f` changed the design to ten scenarios, including hosted recovery, a group Git-checkout lock held for 12 seconds, dead-owner registry reclamation, two-listener/batched wake, and a webhook rejection table. A local HTTP sink was dropped because the helper rejects non-HTTPS URLs; it uses a fetch preload instead. This addresses my missing-seam objection. Team 2 adopted the requirement that replacements fail on pre-fix code and pass on current code before deletion; the registry case needs to detect both `8548de0`'s lost updates and `996bba9`'s prior `ENOTEMPTY`, and a clock-injected wake case must age a live accepted claim past the old 30-second limit. Its 3–4-minute parallel runtime remains an estimate. Team 2's history search found the old source-size budget was raised 50 times in 37 days; I agree an owner-reviewed exception is needed instead of a self-editable cap.
- Team 1 scored 8,723 of 17,094 test lines (51%) as mock/copy/wording/timing/duplicate/trivia, while about 6,400 (37%) are seam-worthy or kept unit bodies. This confirms the bloat but shows why 3,000 lines requires rewriting rather than simply deleting half the files; ~2,400 current kept-unit lines alone exceed Team 2's ~500-line unit estimate. It scored `test/sweep-command.test.ts` as scenario and kept dead-owner reclamation. It would delete `test/open-command.test.ts`, which exposed the index-lock bug on its 14th run, while retaining the 25-line direct `test/git-status.test.ts` regression from `43c01cf`. I checked `git show 43c01cf:ci-repair-notes.md` and agree: finding a bug does not oblige retention of a second costly guard.
