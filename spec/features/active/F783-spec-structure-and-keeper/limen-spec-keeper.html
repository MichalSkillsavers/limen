How agents write specs, and the spec keeper

Agents left spec work half linked: two tickets with the same number, a ticket with no front matter, map files that point at moved tickets. This page shows what an agent sees when it writes a ticket, what now helps it, and the new keeper step that checks the links before a land.

Feature F783 · Limen plant · 6 October 2026

1. What an agent sees

Every agent gets the ticket shape rules in its system prompt. Before this change, no worker was told the four facts it needs at the moment it writes a ticket.

2. Where agents failed

Real misses on this plant. Each one passed every check, because the strict build only warned and nothing at finish or land read tickets.

Misses

  • Two active tickets share F778. The number was taken only on a job branch, so a folder check on main found it free.
  • The plant webhook ticket (F781) was committed with no front matter. The template on main had none yet, so the agent followed it correctly.
  • Map files still cite F728, F740 and F741 at their old paths. Nobody was told to fix the map after a lane move.
  • About 45 tickets needed front matter by hand during the live picture work (F780).
  • 26 of 30 merges on main since 3 October did not use limen land, and 53 direct commits changed specs. A check only in limen land misses most changes.

Help that now exists

  • limen ticket new "what becomes true" takes the next free number. It looks in every lane, in limen/* branches and in job labels, and writes a ticket that passes the strict check.
  • Each strict ticket message ends with fix: and one action.
  • Worker and team coordinator instructions carry a five-line ticket contract: template, number, front matter, place ids, strict check.
  • limen ticket check BRANCH runs the land gate before a hand merge.

3. The spec keeper

Workers do not stop to fix links. After they finish, the coordinator starts one short keeper job. The keeper works on its own branch, so it never touches a running worker.

QuestionDecision
Who starts the keeper?The coordinator, or the group lead for a group. No hook spends a model run on its own. limen land only checks; it never starts a job.
What does it get?One packet in its task: the ticket path, the board, the map folder, the candidate branch and tip, and per job its id, label, state, branch, worktree, session file and task file.
How long?20 minutes by default, on the cheaper model.
What blocks a land?An error on a ticket the branch adds or changes: an unknown place id, a bad field, an active ticket with no front matter, or a new ticket that reuses a number. --yes does not skip it.
What only warns?No touches, a missing or wrong board line, a map source that points at a moved ticket.
How does it avoid running workers?It refuses while a listed job runs, and it commits only on its own branch.
One job or a group?Same command. A group lead passes --group (every member job) and its integration branch with --candidate.

4. Try it

  1. Write a ticket
    limen ticket new "Agents see the map place ids" --lane active --touches limen.commands

    It prints the new ticket path with the next free number.

  2. Check a branch before a merge
    limen ticket check BRANCH

    It prints each ticket problem with its fix, and exits 1 on an error.

  3. Run the keeper after a job
    limen keeper spec/features/active/FNNN-slug/ticket.md --job JOB-ID --engine omp --provider openai-codex --model gpt-6-sol --thinking high

    When it is done, land the keeper job with limen land KEEPER-ID.

5. Limits

  • A hand merge with git merge skips the gate. The coordinator text says to run limen ticket check first. A direct commit on main is checked only when the coordinator runs limen picture build --strict.
  • The keeper fixes links. It does not judge whether the ticket is right, and it does not renumber a taken number; it reports it.
  • The map lives only in the plant and is not committed. Keeper map fixes go to the plant map, not to the branch.
  • A number reserved only on another machine's branch is not seen.
